# V1.6.3 — Realtime Updates

V1.6.3 accelerates game and chat refreshes without moving authority out of Open Shed's Sites APIs or D1 database.

## Product behavior

- A connected table may receive a content-free WebSocket hint when game or chat data changes.
- The browser responds by calling the existing authenticated Sites endpoint and applying only its viewer-specific projection or filtered chat page.
- Game commands, chat messages, reports, mute, block, membership, presence, and every rules decision remain HTTPS/D1 operations.
- The browser keeps low-rate safety polling while realtime is healthy and immediately returns to the original polling cadence when the companion is unavailable.
- Focus, visibility, online, reconnect, duplicate hints, and out-of-order HTTP responses all converge through the same monotonic refresh boundary.

The socket never carries hands, cards, messages, names, player identifiers, game identifiers, join codes, reports, moderation evidence, or authoritative revisions. Its server frames contain only `ready`, `invalidate`, or `resync_required` with optional `game` and `chat` topics.

## Deployment shape

The application remains a Sites deployment. A separate Cloudflare Worker provides one hibernating Durable Object per opaque table room because the Sites storage manifest exposes D1/R2 but not a Durable Object binding. The companion is notification-only; it cannot read or mutate game data.

Sites issues a 30-second one-use, room-bound connection ticket after current-member authorization. The upgrade verifies the exact production origin, an expiry-bound opaque route capability, and the signed ticket before selecting a Durable Object. The response exposes only the public protocol name. Worker observability, invocation-log persistence, exports, and traces remain disabled because the short-lived bearer is necessarily offered in the encrypted WebSocket protocol header. Cloudflare's explicitly attached live-tail stream is a separate privileged, non-persistent debugging surface and must not run or retain output during user traffic.

Post-commit notifications are best effort and are signed over the opaque room, timestamp, random nonce, and exact bounded body. Delivery failure never changes an already committed API response.

## Recovery hardening

- Chat pagination now uses a monotonic D1 allocation cursor rather than timestamp/random-ID ordering.
- A removed 24-hour message no longer invalidates the cursor; an unknown cursor rebases to the latest bounded window with an explicit response header.
- Initial and rebased pages start at the newest bounded messages while preserving chronological display order.
- A replayed gameplay command no longer advances the Activity cursor past events it did not deliver. Polling recovers the accepted command and any intervening moves in order.
- An invalidation arriving during an older in-flight game read queues one trailing authoritative refresh before the socket is considered live.

## Rollout and rollback

Realtime is controlled by an exact-`true` Sites switch and an independently default-off Worker switch. Disabling either side leaves the existing HTTP behavior intact. Polling remains a permanent recovery path rather than a temporary migration aid.

Before enabling production traffic, the release gate requires real Worker/Chromium upgrades, strict rejection and replay tests, content-free frame inspection, a two-player Sites/D1 game-and-chat journey, Worker-outage recovery, confirmation that persistent account/custom logs and exports do not retain the WebSocket protocol bearer, and zero active privileged live-tail clients.
